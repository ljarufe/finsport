## Causas de proceso y recomendaciones para owning chat de F008/F009

1. **Preflight de contrato externo fallido.** El maintainer autorizó desde el inicio GET live acotados de sólo lectura. Se debió probar `ids=` exacto antes de Pass 1; unos pocos GET seguros habrían falsificado la premisa antes del código. Para cada READ externo nuevo/cambiado, verificar forma física, acceso del plan, campos, paginación/retry y costo antes de implementar cuando sea seguro.
2. **Prioridad de recursos equivocada.** Se optimizó ahorrar pocas solicitudes API y se consumió mucho más tiempo de maintainer, múltiples passes/reviews/UAT y tokens Codex. Se agotó la cuota de uso Codex y el trabajo tuvo que pausarse varias horas; no se atribuye un número de horas humanas no medido. Optimizar costo total: GET acotados que cierran incertidumbre material suelen valer más que otro pass, salvo amenaza genuina a cuota crítica.
3. **Blast radius tardío tras falsificación.** Al comprobar UAT que `ids=` no funcionaba, se debió buscar globalmente todo uso productivo y reabrir criterios dependientes antes de Pass 5. Centrarse primero sólo en OPEN dejó invisible el camino no-bet hasta Pass 6.
4. **Invalidación de aceptación omitida.** A37 siguió PASS aun después de que su mecanismo físico `ids=` fuera refutado. Un criterio dependiente de una premisa caída vuelve a PENDING hasta revalidar su reemplazo; este ledger corrige A37.
5. **Review completo como gate normal, no técnica de rescate.** Después de **cada** pass, incluso Pass 1: verificar master/base; revisar diff completo rama-vs-master y todos los archivos acumulados; leer código original relevante fuera del diff; trazar productores/consumidores, contratos externos, ownership/scheduler, cuotas/contabilidad, persistencia/idempotencia, duplicación de límites y aceptación; cerrar UAT independiente antes de decidir otro pass. Un ticket bien definido no elimina acoplamientos ocultos.
6. **Chequeo de frontera compartida.** Si subsistemas forman independientemente la misma solicitud física, preguntar si se están corrigiendo varios consumidores porque la frontera proveedor está duplicada. Preferir helper pequeño para el contrato físico, sin fusionar propietarios de negocio; Capture/Capital/sync día en FS-017 son el ejemplo.
7. **Batching de UAT.** Ante un finding, completar primero todo UAT/review independiente ejecutable y enviar una corrección consolidada. Interrumpir antes sólo si el hallazgo bloquea evidencia dependiente.
8. **Disciplina del harness.** Preferir módulos de tests reales o diagnósticos mínimos. Copiar tests con imports relativos a `tmp/` generó una falla del harness, no del producto, y consumió una iteración evitable.
9. **Regla de recuperación >=Pass 5.** Un pass excepcional debe iniciar con root cause, base/master, diff completo, cierre de contrato externo, blast radius, aceptación invalidada y oportunidad de refactor; su objetivo es cierre técnico, no otro parche local.
10. **Gate pre-PR.** No convertir PR review en fase planificada de descubrimiento. Antes del PR: UAT independiente pre-merge terminado, contratos usados verificados, criterios reconciliados, diff completo revisado, gate verde y ningún fix pre-PR conocido deferido. PR aún puede descubrir hechos genuinamente nuevos.
11. **Método Pass-6 como estándar.** Adaptar explícitamente este review de recuperación al cierre de **cada** pass futuro; la especificación clara no sustituye la búsqueda de acoplamiento, código heredado obsoleto, fronteras duplicadas ni premisas de tests inválidas. Promover estas recomendaciones en el owning chat de F008/F009; no editar esas fuentes aquí.
